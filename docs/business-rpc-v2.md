# Business RPC Stream V2

Business RPC V2 shares the `business_tcp` listener between device authentication, UDP verifier resolution, authorization control, and confirmed events. The wire protocol is four byte big endian payload length followed by JSON. The length excludes the prefix; zero length, oversized frames, invalid JSON and unknown fields are rejected. V2 uses `hello.version = 2` independently of the V1 public protocol version. See `netbaiot-protocol::business_rpc` for the authoritative frame and method DTOs.

## Roles, identity and connection behavior

A V2 `Hello` requests `events`, `auth_control`, or `multiplexed`. The server returns `Ready` with a connection epoch and negotiated limits after authenticating the business principal. An event subscription uses `Subscribe` / `Subscribed`, then `Event` / `EventAck` or `EventNack`. The server owns at most one event in flight per subscription. `device.authenticate` and `device.resolve_verifier` are server requests to the application; multiple requests can run while an event waits for ACK. `auth.sync` and `auth.invalidate` are application requests to the server. `Ping` / `Pong`, `Cancel`, and `GoAway` are connection control frames.

The server has separate bounded control, authentication, and event output queues. Control and authentication retain their own capacity during an event ACK wait. Priority only affects frames not yet written; one large frame already in TCP can still delay another. For stronger byte stream isolation in production, use one `auth_control` and one `events` connection to the same listener. The provider is unique, with a connection epoch lease: a second active provider is rejected, and an old disconnect cannot release its replacement. V1 and V2 subscribers also contend for the same stable `tcp-rpc` sink owner. A V2 `events` filter never silently discards accepted required work.

Production V2 requires mTLS. The server verifies the client certificate and maps its SHA-256 fingerprint to an explicitly configured `BusinessPrincipal`; CA membership alone grants no role. The SDK verifies the server name and CA and presents its own certificate. A principal defines role, `primary` provider or `tcp-rpc` sink binding, allowed methods, global or tenant scope, and optional expiry. Hello claims never grant additional permissions. Loopback plaintext requires the separate `development_token_env`; neither management nor V1 token authorizes V2. Existing V1 remains available with no `business_rpc` configuration, or on the same loopback plaintext listener when `allow_v1` is true. Mixed mode dispatches by the versioned first frame. TLS V2 does not allow V1 fallback.

## Authentication and synchronization

`device_auth: "business_rpc"` uses the existing bounded AuthCache and single flight misses. MQTT and TCP authenticate once per connection. UDP verifier cache hits verify HMAC locally; only misses call `device.resolve_verifier`. A provider must finish reset `auth.sync` after each connection. The server invalidates the local auth cache, live device sessions, and persistent MQTT sessions through the same domain boundary used by management HTTP. The provider becomes Serving only after the client receives the sync response and confirms it with `Ping` / `Pong`. New cache misses fail closed until Serving. `auth.invalidate` must be sent after the authority commits its revision; the server applies it before returning success. Duplicate revision is idempotent, while a gap or different incarnation requires reset sync.

The configured `max_auth_control_offline_ms` is a finite offline grace for existing authorization. New misses fail immediately while the provider is gone. Unexpired positive cache entries may remain usable only during the grace; at its end the server runs full invalidation and disconnects affected sessions. Zero disables the grace. Reconnect reset intentionally forces device reauthentication to cover revocations missed during disconnection. No auth cache, credential, or verifier is persisted in the restart spool. Explicit device rejection maps to `Authentication`; unavailable provider, timeout, overload, invalid or unauthorized response do not create negative cache entries. Responses must match the request ID, connection epoch, method, scope, and minimum revision.

## Events and durability

The application calls `BusinessDelivery::ack()` only after its transaction commits. A socket write or delivery to a callback is not an ACK. `nack`, disconnect, timeout and unobserved ACK leave responsibility with EventBus for its bounded retry policy. `event_id` is stable across retries and restart replay; `delivery_id` may change. Consumers must deduplicate by `event_id`. A successful planned restart drains required work or durably spools remaining work. Abrupt process or power failure can lose bounded unspooled memory traffic. No exactly once or crash durability guarantee is made.

## Configuration and SDK

The four concerns are independent: `business_tcp` selects the listener, `business_rpc` selects V2 transport and identity, `device_auth` selects `static`, `http`, or `business_rpc`, and `event_delivery` selects `http`, `business_rpc`, or development audit. Supported combinations include RPC auth with RPC events, RPC auth with HTTP webhook, HTTP auth with RPC events, and static auth with RPC events. Set `delivery_url` only with `event_delivery: "http"`, and `auth_provider_url` only with `device_auth: "http"`; ambiguous legacy/new settings are rejected. Without `business_rpc`, legacy business stream behavior remains. For loopback V2, start from `configs/development.json`, set `business_tcp`, `business_rpc: {"version":2,"tls":null,"development_token_env":"NETBAIOT_BUSINESS_RPC_TOKEN"}`, and choose the sources explicitly. Set that env variable to a distinct secret. Production uses `business_rpc.tls` with `certificate`, `private_key`, `client_ca`, `require_client_certificate: true`, and `identities` with `certificate_sha256`, `principal_id`, `role`, `provider_id`/`sink_id`, method lists, scope, and optional `expires_at_ms`.

Defaults: 8 business connections, 128 authentication requests in flight, 1 event in flight, 4 KiB Hello, 16 KiB auth frame, 8 MiB event frame, 5 s heartbeat, 30 s offline grace. RPC deadline uses the configured authentication timeout; event ACK uses sink timeout. These are resource limits, not measured throughput. Use `BusinessRpcClient::connect(config, handler)` and its independent driver; `wait_ready` waits for sync and subscription. The event receiver is optional for auth progress. `invalidate(revision, scope)` awaits server application. `shutdown` stops owned work. The runnable in-memory example supports `multiplexed`, `dual`, `auth_webhook`, and `invalidate` modes:

```sh
cargo run --locked -p netbaiot-client --example business_rpc_v2 -- multiplexed
```

Set `NETBAIOT_BUSINESS_RPC_ADDRESS`, `NETBAIOT_BUSINESS_RPC_TOKEN` (or the example's CA/client cert environment variables), `DEMO_DEVICE_SECRET`, `DEMO_VERIFIER_KEY_HEX`, `DEMO_CREDENTIAL_ID`, `DEMO_TENANT_ID`, `DEMO_PRODUCT_ID`, and `DEMO_DEVICE_ID` before running. The example authority is in memory; production must back it with the application's own authorization state. For `auth_webhook`, configure the gateway's HTTP event delivery separately. The `disable` and `enable` commands update the demo revision and send `auth.invalidate`.

## Errors and operations

`device_rejected` means the credential/device was explicitly rejected. `unavailable`, `timeout`, `overloaded`, `forbidden`, `invalid_request`, `stale_revision`, and `internal` denote transport, capacity, permission, synchronization or service failures. V2 responses carry the original request ID and method. The SDK treats authorization and protocol errors as terminal and retries transient connection failures with bounded backoff. Examine `/api/v1/status` for `business_auth_serving` and pending count; `/api/v1/metrics` exposes fixed-name business RPC connection, sync, invalidation, timeout, overload, late response, queue count/bytes, pending count/bytes and ACK latency series. Device IDs, request IDs and credentials are not metric labels. An unready provider usually needs a successful reset sync. A rising timeout or queue series suggests a slow authority or consumer; inspect application processing and mTLS identity/role mapping.

This version does not move management HTTP APIs or commands to RPC and does not add provider balancing, consumer groups, multi-node session routing, gRPC, WebSocket, QUIC, new binary encoding, or a wider event window.
