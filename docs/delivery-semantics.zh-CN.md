# 投递语义

## EventAccepted

事件只有在完成认证/授权、协议和 codec 校验、路由选择、数量/字节接纳，以及为每个需确认的必需 sink 原子预留入队容量后才算接受。在此之前，生产者仍需负责重试。此后，计划关机必须对所有待处理必需责任完成 ACK 或写入重启 spool。

MQTT QoS1 PUBACK 和 HTTP `202 Accepted` 精确表示越过这一边界。它们都不代表业务应用已处理或持久化事件。

## 正常投递和重启恢复

正常运行以内存处理为主。必需 sink 显式 ACK；尽力而为的 sink 可按有界溢出/失败策略丢弃。重试会保留 `event_id`，并受数量/状态/速率限制，使用指数全抖动策略，不会为每次重试单独创建任务。普通重试次数/事件期限耗尽后，需确认的必需工作会进入有界、低频的降级重试通道；它仍由进程持有，可以在运行时恢复。延迟重试按就绪时间选择，而不是按队列位置，因此较早但尚未到期的重试不会阻塞后续已就绪事件。

计划重启会 drain 必需工作。仍待处理或 inflight 状态不确定的投递会 fsync 到本地重启 spool，并以相同 ID 重放。这提供了可安全进行优雅重启的至少一次投递。可能发生重复投递，包括业务已处理事件、但其 ACK 丢失的情况。

若 fsync/原子提交失败，进程会继续运行并保持未就绪，保留 worker 和内存中的责任，并以有界频率重试。只有必需工作完成 drain 或权威快照提交成功后才能退出。

SIGKILL、进程/操作系统崩溃、断电或硬件故障都可能导致仍仅保存在内存中的有界已接受事件丢失。NetbaIoT 不承诺崩溃持久性或恰好一次投递。需要持久正确性的消费者必须按 `event_id` 去重，并在业务系统中持久化数据。

## 命令

命令是易失的在线会话操作。接纳命令表示某个当前连接的本地 MQTT/TCP 会话已将命令放入其数量和字节数有界的队列。设备离线时返回不可用。传输写入（`SENT`）、MQTT PUBACK/设备收到命令，以及设备执行 ACK 是不同阶段。执行结果会以相同的 `command_id` 作为 `DeviceEventKind::CommandAck` 返回。
