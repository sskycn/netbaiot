# NetbaIoT v0.2.4

[中文](v0.2.4.zh-CN.md)

## Highlights

NetbaIoT now prioritizes Linux production deployments, with mandatory native
x86_64 and ARM64 release archives. This release also includes bounded EventBus
accounting, tenant backlog quotas, and business sink outage handling merged since
v0.2.3. It remains a database-free, memory-first, single-node IoT gateway with
embedded MQTT 3.1.1/5.0, framed TCP, and authenticated UDP.

## Platform support and release assets

- Linux x86_64 and ARM64 are the official production targets. Both archives must
  pass native quality/recovery tests, release builds, extracted binary startup,
  MQTT/TCP/UDP end-to-end smoke, and exact-set SHA256 verification before publishing.
- Required assets are `netbaiot-v0.2.4-x86_64-unknown-linux-gnu.tar.gz`,
  `netbaiot-v0.2.4-aarch64-unknown-linux-gnu.tar.gz`, and `SHA256SUMS`.
  The GNU binaries are built on Ubuntu 24.04; verify loader/glibc compatibility
  before deploying to another distribution.
- macOS x86_64 and Apple Silicon remain development/test platforms with source
  builds, native development checks, and independent optional build artifacts.
- Windows x86_64 MSVC is experimental. Source builds and existing recovery/network
  compatibility remain available, without a production stability or per-release
  binary promise. Independent manual checks report failures normally.
- macOS/Windows failures do not block Linux releases. Historical release assets
  are unchanged. The shared target policy and strict archive path, link, format,
  architecture, and checksum validation prevent incomplete or mislabeled packages.

See [platform support](../platform-support.md) for build and deployment details.

## Reliability and resource safety

- Required sink responsibilities use incrementally maintained accounting. Duplicate
  or stale completions cannot release ownership twice; retries, pauses, and spool
  recovery retain accepted responsibility until acknowledgement.
- Accepted event backlog is bounded per tenant by count and serialized bytes,
  alongside existing global and independent sink limits. Admission and restore
  remain atomic, with rollback on failure.
- Required sinks pause after permanent or repeated failures and resume through a
  bounded probe. HTTP failures have explicit classifications, while bounded
  `Retry-After` delta-seconds for 429/503 respect the configured retry ceiling.
  A socket write or failed callback never becomes a business acknowledgement.
- Sink diagnostics include pending age, pause state, and a closed failure-reason
  vocabulary. Identifiers and sink URLs remain outside metric labels.
- Real TLS MQTT QoS1/webhook outage and planned-restart regression scenarios cover
  stable event IDs, acknowledged delivery, resource cleanup, and recovery ownership.

## Performance

EventBus usage reads avoid rescanning accepted backlog, and webhook serialization
borrows the existing event rather than constructing an additional JSON tree.
The [engineering report](../engineering-optimization.md) records local allocation,
latency, outage, and restart measurements, including tradeoffs and measured commits.
These are subsystem/local measurements, not production capacity or SLA claims.

## Compatibility

- Workspace crates advance from 0.2.3 to 0.2.4. DeviceEvent, MQTT, TCP/UDP, Business
  RPC V3, EventAccepted, business ACK, online commands, and TLS/management boundaries
  keep their existing wire and responsibility semantics.
- Sink delivery metadata and management diagnostics are additive. Existing
  `EventSink::deliver` implementations use the default detailed-delivery adapter.
- Configuration gains `limits.event_queue_max_count_per_tenant` (default 16384) and
  `limits.event_queue_max_bytes_per_tenant` (default 67108864). Existing configurations still
  parse, but installations with increased global budgets should review the new
  per-tenant limits. See [configuration](../configuration.md).
- Recovery formats remain EventBus NBSP v3 and MQTT NBMQ v6. Older or unknown
  formats fail explicitly; there is no legacy parser fallback or runtime migration.
  Do not reduce limits below responsibilities already committed in recovery files.

## Upgrade notes

1. Download the archive matching the host architecture and verify its SHA256
   against `SHA256SUMS`; on Linux use `sha256sum -c SHA256SUMS --ignore-missing`
   while retaining the published archive filename.
2. Review tenant backlog budgets, required sink failure behavior, and the GNU
   binary's distribution requirements before replacing binaries.
3. Quiesce the old process and wait for successful graceful shutdown. Preserve
   the configuration and supported recovery files; never discard unacknowledged
   required work to bypass a recovery or capacity error.
4. Replace `netbaiot-server` and `netbaiot`, restart, then verify readiness and
   required sink acknowledgements. Business consumers must handle replay by
   stable `event_id` idempotently.

## Known limitations

- Single node; no clustered sessions, horizontal HA, or cross-node command routing.
- No MQTT-SN, WebSocket, shared subscriptions, Topic Alias, Subscription Identifier,
  Enhanced Authentication, bridge mode, or `$SYS` services.
- UDP is authenticated but unencrypted, with no session or command downlink.
- Planned restart recovery is not crash durability. Abrupt process, machine, or
  power failure can lose bounded recent in-memory events and MQTT state.
- Offline command storage, historical telemetry, and business persistence remain
  external. The project is pre-1.0 and does not provide a production capacity or
  long-term API compatibility guarantee.
